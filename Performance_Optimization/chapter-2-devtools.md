# 📌 Chapter 2: 성능 분석 도구 마스터하기 (DevTools & Lighthouse)

웹 서비스의 성능 병목을 정확하게 진단하고 원인을 추적할 수 있도록, 크롬 개발자 도구(Chrome DevTools)의 핵심 패널 및 성능 지표 모니터링 분석법을 숙지해야 합니다.

---

## 1. Performance 패널을 이용한 CPU / Flame Chart 분석

`Performance` 패널은 브라우저의 런타임 성능을 실시간 프레임 단위로 녹화하여 자바스크립트 실행 시간, 스타일 재계산(Reflow), 페인팅, 가비지 컬렉션 등 모든 브라우저 메인 스레드 태스크를 밀리초(ms) 단위로 추적하는 정밀 진단 도구입니다.

```
[Record] 버튼 클릭 ➔ 랙(Lag)이 발생하는 특정 사용자 동작 재현 ➔ [Stop] 버튼 클릭 ➔ 데이터 분석
```

### 1) 분석 핵심 워크플로우
1. **CPU Throttling 설정**: 개발 중인 고사양 PC 환경은 일반 사용자의 모바일 성능보다 월등히 좋기 때문에, CPU 스로틀링을 `4x slowdown` 혹은 `6x slowdown`으로 걸어 분석 환경을 일반 모바일 기기와 유사하게 시뮬레이션해야 합니다.
2. **Record 실행**: 레코딩을 가동하고 성능 정체 현상이 발생하는 특정 동작(예: 리스트 정렬, 페이지 스크롤, 대용량 모달 열기 등)을 재현한 뒤 기록을 중지합니다.
3. **주요 차트 영역 확인**:
   * **FPS (Frames Per Second)**: 상단 그래프에서 FPS 바가 빨간색으로 채워지는 부분은 60fps 미만으로 떨어져 화면이 버벅인(Jank) 시점입니다.
   * **CPU**: 노란색(Scripting), 보라색(Rendering), 초록색(Painting) 그래프의 점유 비중을 시각적으로 파악합니다.
   * **Main (메인 스레드)**: 메인 스레드의 태스크 흐름(Flame Chart)이 계층적으로 나열됩니다. 특정 함수 바(Bar)의 우측 상단에 빨간색 삼각형 모서리가 노출된다면, 해당 연산이 50ms 이상 메인 스레드를 독점한 **Long Task**임을 의미합니다.
4. **하단 상세 정보 탭 분석**:
   * **Summary**: 선택된 영역 내 스크립트 실행, 렌더링, 페인트, 대기 시간 비율의 통계를 보여줍니다.
   * **Bottom-Up**: 연산 시간이 가장 오래 걸린 함수를 하향식(Bottom-Up)으로 추적하여, 실제로 연산 지연을 유발한 근원(Root) 소스 코드가 무엇인지 역추적하도록 돕습니다.

## 2. Lighthouse 패널을 이용한 핵심 지표 분석

Lighthouse는 구글에서 제공하는 오픈소스 품질 자동화 진단 도구로, 사용자 경험을 반영하는 3가지 핵심 성능 지표인 **Core Web Vitals**를 집중적으로 진단합니다.

### 📊 Core Web Vitals 핵심 지표 기준

| 지표명 | 측정 기준 | 목표값 (Good) |
| :--- | :--- | :--- |
| **LCP (Largest Contentful Paint)** | 뷰포트 내 가장 큰 콘텐츠(대형 이미지나 텍스트 블록)가 화면에 완전히 그려지는 시점 (로딩 속도 체감) | **2.5초 이하** |
| **INP (Interaction to Next Paint)** | 사용자가 클릭, 탭, 키 입력을 한 뒤 다음 화면의 픽셀 업데이트가 완료될 때까지 걸린 총 지연 시간 (인터랙션 반응성) | **200ms 이하** |
| **CLS (Cumulative Layout Shift)** | 로딩 과정 중 예기치 못한 레이아웃의 급격한 흔들림/움직임 점수 (시각적 안정성) | **0.1 이하** |

### 🔍 분석 및 개선 가이드 요령
Lighthouse 검사 보고서 하단에 노출되는 **"Opportunities" (추천 제안)** 및 **"Diagnostics" (진단)** 섹션을 참고하면, "차세대 포맷 이미지 사용", "렌더링 차단 리소스(CSS/JS) 제거" 등 해당 페이지 성능 점수를 끌어올리기 위한 구체적인 실행 계획을 명확하게 도출할 수 있습니다.

## 3. Network 패널과 리소스 폭포수(Waterfall) 읽기

Network 패널의 **Waterfall(폭포수) 차트**는 각 리소스(HTML, JS, CSS, 이미지)가 언제 요청되었고, 다운로드 및 대기에 얼마나 많은 시간이 소비되었는지 나타내는 핵심 타임라인 맵입니다.

### 1) 네트워크 대기 지표 해석
* **Queueing**: 브라우저가 리소스 요청을 대기 큐에 적재해 두고 기다리는 시간입니다. 
  * HTTP/1.1은 동일 도메인당 최대 동시 소켓 커넥션 개수가 6개로 제한되어 있으므로, 한 번에 수십 개의 자원을 요청하면 7번째 파일부터는 긴 Queueing 시간 병목이 관찰됩니다. (HTTP/2 다중화를 도입하여 해결 가능)
* **TTFB (Time to First Byte)**: 브라우저가 서버에 최초 요청을 보내고 첫 번째 응답 바이트를 수신하기까지 걸린 지연 시간입니다. 백엔드 API 서버의 연산 속도 둔화나 네트워크 라우팅 지연 시 늘어납니다.
* **Content Download**: 실제 네트워크 대역폭을 통해 리소스 바이너리를 클라이언트로 전달받는 시간입니다. 파일 용량이 거대하거나 사용자 대역폭이 좁을 때 지연됩니다.

### 2) 성능 진단 요령
* **HTTP/2 & HTTP/3 사용 여부**: `Protocol` 열을 활성화하여 병렬 다중 전송이 실시간 가동 중인지 체크합니다.
* **네트워크 스로틀링(Throttling)**: 개발 환경의 기가비트 광랜 대신 `Fast 3G` 또는 `Slow 3G` 프로필로 제한하여, 열악한 통신 환경의 실사용자가 겪는 폭포수 흐름을 똑같이 추적해야 합니다.

## 4. Coverage 패널을 이용한 Unused Code(JS/CSS) 추출

모던 웹은 싱글 페이지 애플리케이션(SPA) 구조상 당장 해당 화면에 사용되지 않는 페이지의 컴포넌트 코드까지 초기 번들에 묶여서 한꺼번에 다운로드되는 경향이 강합니다. `Coverage` 패널은 **현재 화면을 렌더링하고 상호작용하는 데 실제 로드된 코드 중 몇 %가 실행되었는지** 정확하게 진단합니다.

### 1) 미사용 코드 분석 절차
1. 크롬 개발자 도구 설정(우측 상단 점 3개) ➔ `More tools` ➔ `Coverage`를 활성화합니다.
2. 새로고침 아이콘(Start instrumenting coverage and reload page)을 눌러 초기 로드를 캡처합니다.
3. 리스트에 잡힌 파일별로 **"Unused Bytes" (미사용 바이트)** 비율이 얼마나 되는지 확인합니다.
4. 분석할 대형 JS/CSS 파일을 더블클릭하면 소스 코드 뷰어 좌측 라인 옆에 **초록색(실행됨)**과 **빨간색(실행되지 않음)**이 실시간 시각화됩니다.

이 패널에서 빨간색 미사용 바이트 비율이 높은 정적 파일들은 **코드 분할(Code Splitting)**을 적용해야 할 일차적인 리팩토링 타깃으로 낙점됩니다.

## 5. Vite / Webpack Bundle Analyzer 시각화 도구 활용

번들 분석도구는 번들링 과정을 거친 최종 프로덕션 빌드 결과물(JavaScript)의 물리적인 크기 구성을 직관적인 사각형 트리맵(Treemap) 차트로 시각화해 줍니다. 

### 1) 분석의 목적
* 어떤 외부 npm 의존성 라이브러리가 과도하게 큰 부피를 차지하고 있는지 색출합니다.
* 트리 셰이킹이 정상 작동하지 않는 무거운 날짜/유틸리티 패키지를 확인해 가벼운 Day.js 등으로 대체 설계를 실행하는 결정적 데이터를 확보합니다.

### 2) Vite 환경 설정 예시
Vite 환경에서는 `rollup-plugin-visualizer` 플러그인을 설정해 빌드 성공 시 `stats.html` 리포트를 확보할 수 있습니다.

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [
    vue(),
    visualizer({
      open: true, // 빌드 완료 시 브라우저에 리포트 즉시 노출
      filename: 'dist/stats.html',
      gzipSize: true,
      brotliSize: true
    })
  ]
});
```

## 6. Vue / Pinia DevTools 활용법

개발 환경 전용 익스텐션인 `Vue Devtools` 및 `Pinia Devtools`를 사용해 가상 돔 렌더링 주기와 상태 변화를 정밀 트래킹할 수 있습니다.

### 1) 핵심 디버깅 기능
* **Component Inspector**: 돔 트리를 탐색하며 컴포넌트에 주입된 반응형 상태(Reactive State)와 Props를 검사하여 불필요한 프롭스 전달 구조를 디버깅합니다.
* **Timeline (Performance Profiling)**: Vue 컴포넌트 내부의 `Render`, `Patch`, `Update` 연산 시간을 실시간 차트로 캡처합니다. 어떤 반응형 변수의 변화가 원인이 되어 무관한 하위 컴포넌트들까지 대대적으로 재렌더링시키는 낭비(**Over-rendering**)를 범하고 있는지 한눈에 추적하도록 지도 맵을 그립니다.
* **Pinia Inspector**: 전역 스토어 상태 변경과 액션(Actions) 호출 로그를 트래킹하여, 사용자 인터랙션 1회당 Pinia 액션이 중복/반복 수행되거나 불필요한 무한 반응 루프에 빠지는 현상을 색출합니다.
