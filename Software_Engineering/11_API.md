# API (Application Programming Interface)

> [!note]
> **API(Application Programming Interface)**: 서로 다른 소프트웨어 시스템이 서로 소통하고 데이터를 주고받을 수 있도록 돕는 연결 다리로, 사용자의 입력을 전달하고 서버로부터 데이터를 받아오는 통로이다.

API를 어떻게 설계하고 코드에서 어떻게 관리하느냐에 따라 애플리케이션의 전체 구조와 유지보수성이 달라진다. 다만, API를 관리하는 구조에는 정해진 방법은 없다.

## 간단한 API 요청

애플리케이션의 규모가 크지 않은 경우, API 요청은 디렉터리나 함수로 관리하는 것보다 필요한 곳에서 바로 호출하는 것이 좋다. 그러나 페이지가 늘어나고 동일한 API 요청이 많아져 중복이 발생하면 그때 중복을 제거하기 위하여 API 요청을 함수로 만들고 디렉토리와 파일로 구분하는 것이 좋다.

## 리포지토리 (Repository)

> [!note]
> **리포지토리(Repository)**: 서버와의 통신 및 데이터 접근 로직을 UI 컴포넌트와 분리하여 관리하는 아키텍처 설계 방식으로, 데이터베이스로 대표되는 외부 자원을 다루는 방법을 캡슐화하여 리포지토리를 사용하는 모듈이 복잡하지 않고 단순하게 외부 자원을 다룰 수 있게 한다.

ORM은 관계형으로 정의된 데이터베이스의 데이터를 서버에서 사용하는 객체지향의 객체로 매핑하는데 도움을 주는 기술이다. ORM은 리포지토리의 역할을 담당하는 기능을 다수 가지고 있다. 따라서 ORM을 사용하면 리포지토리가 갖는 대부분의 역할을 담당하게 되고 별도의 리포지토리가 필요하지 않을 수 있다.

결국, 리포지토리는 외부에 데이터를 요청하고 응답하는 로직과 데이터를 매핑하는 로직을 관심사에 맞게 분리하기 위하여 사용한다. 이를 통하여 클라이언트가 데이터베이스와 같은 외부 API를 직접 다루지 않도록 한다.

## API 요청 흐름

API 요청을 여러 곳에서 하고 요청이 중복되면 복잡해지고 관리하기 어려워진다. 특별히 API 요청은 프론트엔드 애플리케이션이 동작하기 위한 데이터를 관리함에 있어 필수적인 영역이기에 반드시 관리해야 한다.

## 리포지토리를 활용한 API 요청 흐름 관리

API를 요청하고 응답받을 때, 뷰가 데이터를 전달하면 요청하기 적절한 형태로 바꾸고 응답을 받으면 뷰가 사용하기 좋은 형태로 변환한다. 외부 자원에 접근하는 방법을 직접 구현하거나 관리하지 않고 사용하여 자원에 접근하는 도구가 바뀌어도 뷰에 미치는 영향을 제한한다.

결국 리포지토리 계층은 복잡한 외부 자원 접근과 데이터 준비 과정을 뷰로부터 숨기고 관리하는 방법이다. 리포지토리는 API에 접근하는 기술 자체를 다루지 않기에 인터페이스가 바뀌지 않는 한 영향을 받지 않다. 또한 리포지토리는 요청 및 응답 데이터를 다루기 위하여 DTO 또는 매퍼(Mapper)를 사용한다.

리포지토리 구현은 일종의 추상화 계층으로서 상황에 맞게 적절한 방법을 사용한다.
