# 폴더 구조 (Folder Structure)

폴더 구조는 흩어져 있는 정보를 분류하는 기준이기에 적절한 분류 기법은 필수적이다. 그러나 대부분의 경우 자신이 속한 조직의 상황의 특수성을 반영하거나 지나치게 어려운 개념을 담기에 프론트엔드 애플리케이션을 위한 적절한 폴더 구조를 찾기는 어렵다.

폴더를 단순한 파일 묶음이 아닌, 하나의 모듈로서 이해하면 폴더 구조에 대한 여러 개념들을 이해할 때 도움이 된다.

## 역할 중심 구조와 기능 중심 구조

폴더 구조를 설계하는 접근법은 크게 "파일의 역할을 기준으로 묶는 방법"과 "파일이 구현하는 기능을 기준으로 묶는 방법"이 있다. 이들을 각각 계층 중심 구조와 기능 중심 구조라고 한다.

### 역할 중심 구조

역할 중심 구조는 프론트엔드 어플리케이션을 다룰 때 가장 익숙한 방법으로, 애플리케이션을 구성하는 코드를 `component`, `hooks`, `apis`, `utils`와 같이 역할에 따라 구분한다.

이러한 방식은 구현 속도가 빠르다는 장점을 가진다. 그러나 특정 기능을 파악하기 위해서는 여러 역할 폴더를 살펴봐야 하고 인지 부하가 높아지며 한 기능을 수정하기 위해 여러 폴더에 위치한 여러 파일을 수정해야 한다.

### 기능 중심 구조

기능 중심 구조는 특정 기능을 구현하는데 필요한 모든 코드를 하나의 폴더에 모아둔다. 예를 들어 상품 상세 기능에 필요한 컴포넌트, 훅, API 호출 함수를 모두 `productDetails` 폴더 안에서 관리한다.

이러한 방식은 응집도가 높아 기능의 맥락을 파악하기 쉽고 수정으로 인한 영향을 제한하기 쉬우나, 공통 유틸리티 함수나 커스텀 훅의 경우 기능 구조 유지를 위해 각 기능 폴더에 중복으로 구현해야 한다. 이를 폴더 밖으로 옮기면 역할 중심으로 관리되기 때문이다.

## 폴더 구조를 관리하기 위한 한 가지 아이디어

> [!tip]
> **폴더 구조를 관리하기 위한 한 가지 아이디어**: "기능으로 나누고, 기능 내부는 기능 및 역할로 나눈다" 라는 원칙을 프랙탈 형태로 적용하는 것이다.

이 방식은 하나의 기능 폴더를 모듈로서 다루며, 배럴 패턴을 통해 모듈화 및 캡슐화를 하고 응집도를 높인다. 가능으로 분리하기 모호하거나 비용이 높아 분리할 여력이 안 된다면 먼저 역할 구조를 활용하고 그리고 추후 필요에 따라 기능 구조로 전환하는 것이 좋다.

## 폴더의 위계와 의존성 방향

폴더 수준을 통한 의존성 관리 원칙은 "아래를 향하는 의존성을 만들지 않는다"이다. 파일은 자신보다 상위 수준에 있거나 특정 관계에 있는 파일에만 의존할 수 있다.

접근 가능한 범위를 제한하여 파일의 의존 관계를 전보다 수월하게 파악하고 관리할 수 있다. 이를 위하여 현재 접근이 필요한 수준에 맞춰 파일과 폴더를 위치시키고 수준을 올릴 필요가 있을 때 필요한 수준만큼 올려야 한다.

## 어떤 모습으로 협업할까?

폴더 구조를 관리하기 전 "콘웨이 법칙"을 참고하면 유익하다.

> [!tip]
> **콘웨이 법칙**: "시스템을 디자인하는 조직은 그 조직의 커뮤니케이션 구조를 닮은 구조를 디자인하는 것이다."

폴더 구조를 다룰 때 중요한 것은 방법 그 자체보다 시간의 흐름 또는 조직의 변화에도 불변하는 폴더 구조 관리 원칙이 무엇이고, 변화에 적응하기 위해 어떤 방법을 사용할지 결정하는 것이다.

## 너무 오래 고민하지 않기

폴더 구조를 어떻게 잡으면 좋을지, 무엇을 참고하면 좋을지를 살펴보았는데, 결국 가장 중요한 것은 "너무 오래 고민하지 않기"이다.

널리 알려진 폴더 구조 접근법은 거의 없기에, 또한 경험을 기반으로 추론할 뿐이기에 미리 겁먹거나 경솔하지 말고 더 중요한 문제에 집중하면 된다.
