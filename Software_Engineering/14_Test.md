# 테스트 (Test)

테스트는 소프트웨어의 버그를 발견하는데 도움이 되고 작성한 코드에 문제 없는지 빠르게 피드백을 받을 수 있으며 리팩토링을 효율적으로 수행할 수 있게 한다.

이처럼 테스트는 장점이 많으나 장점을 체감하기 어렵고 테스트 작성에 많은 비용이 들기에 실제로 적용하는 것이 쉽지 않다.

## 테스트 비용

테스트를 작성하는 데는 다양한 비용이 따른다. 이 비용을 잘 관리한다면 테스트 도입의 장벽이 낮아지고, 만족할 수 있는 테스트 수준을 정하는 데 도움이 된다.

### 테스트를 만드는 비용

테스트는 테스트 대상의 사용자를 만드는 것과 유사하다. 테스트를 작성하다 보면 적절하지 않은 네이밍 등의 불편한 요소들을 인지하게 되고 피드백을 받아 코드를 수정하게 된다. 이러한 과정이 기대보다 더 번거롭고 부담스럽게 느껴진다.

### 유지보수 비용

테스트를 작성하고, 그대로 동작하는 코드를 작성했다고 끝이 나는 것이 아니다. 테스트 역시 관리해야 할 소프트웨어이며, 테스트 코드는 테스트 대상에 의존하기에 테스트 대상이 변하면 테스트 코드도 영향을 받는다.

따라서 테스트 작성 뿐만 아니라, 유지 및 관리에도 비용이 든다.

### 테스트를 통해 다루는 경우의 수에 대한 고민

테스트를 작성하다 보면 버그 발생 가능성이 있는 코드가 계속 보여, 다른 경우를 놓치지 않았는지 고민하게 된다. 모든 경우의 수를 검증하려 하면 테스트 대상과 테스트 코드는 점점 비대해지며 이는 기능 구현보다 테스트 작성이 더 오래 걸리는 문제가 발생한다.

## 테스트 수준을 활용한 비용 관리

결국, 여러 가지 테스트 비용으로 인하여 테스트 작성이 멀고 어렵게 느껴진다. 소프트웨어 테스트에는 여러 종류와 수준이 있다. 프론트엔드에서 테스트 수준은 보통 E2E 테스트, 통합 테스트, 단위 테스트로 구분된다.

- E2E 테스트(end-to-end): 사용자 관점의 테스트, 애플리케이션이 처음부터 끝까지 잘 동작하는지 검증한다.
- 통합 테스트(integration): 둘 이상의 객체 또는 함수가 테스트하려는 동작을 위해 협력할 때 객체, 함수를 활용한다.
- 단위 테스트(unit): 함수, 클래스, 모듈, 컴포넌트 등의 한 단위를 검증한다.

## 중요한 대상을 먼저 테스트하기

테스트를 작성할 때, 많은 코드 중 어떤 코드를 먼저 테스트해야할 지를 결정해야 한다. 이때 결정하는 중요한 기준은 "모듈이 안정적인가?"이다. 안정적인 모듈은 다수의 모듈이 의존하는 대상이다. 모듈 자체가 안정적이라는 것이 아니라 다수가 의존하기에 쉽게 바꿀 수 없기에 안정적인 것이다.

비즈니스 로직, 유틸맅티 함수, 애플리케이션 전반에서 사용되는 공용 컴포넌트 등은 안정적인 모듈이다. 안정적인 모듈이 다른 모듈에 의존하지 않는다면 이 모듈은 독립적인 모듈이다. 독립적인 모듈은 테스트하기 수월하다.

안정적이지만 독립적이지 않는 모듈의 경우, 통합 테스트를 하는 것이 효과적일 수 있다. 이 모듈과 의존하는 모듈을 함께 통합 테스트를 할 수 있다면 안정적이고 독립적인 모듈을 테스트하는 것과 같은 효과를 낼 수 있다.

만약 안정적인 모듈을 테스트할 때 의존하는 다른 모듈과 함께 테스트하기에 어려움이 있다면 해당 모듈을 흉내 내는(mocking) 다른 모듈을 주입하여 테스트할 수 있다.

## 스텁과 목 (Stub & Mock)

스텁(Stub)과 목(Mock)은 테스트 더블(test double)로서 테스트 대상(SUT)을 검증할 때 SUT가 의존하는 대상들을 흉내낸다. 이때, 테스트 더블이란 테스트를 어렵게 만들거나 방해하는 요소들을 대역하여 테스트 대상이 테스트 환경에서 독립적으로 자신의 역할에 집중할 수 있게 한다.

스텁과 목은 흉내내는 대상이 다르다.

- 스텁(stub): SUT가 입력 데이터를 얻기 위해 상호작용하는 의존성을 흉내낸다.
- 목(mock): SUT가 상태를 변경하기 위해 상호작용하는 의존성을 흉내내고, 출력을 검증한다.

## 프라이빗 메서드는 테스트하지 않는다.

테스트를 작성하다 보면 SUT가 사용하는 내부 로직을 테스트해야 할지 고민될 때가 있다. 클래스에서 내부 구현을 다루는 방법 중 하나인 프라이빗 메스드를 테스트해야 하는지 고민이 될 수 있다.

그러나, 프라이빗 메서드는 테스트하지 않으며, 뿐만 아니라 내부 구현 또한 테스트하지 않는다. 캡슐화가 깨지면 내부 구현에 대한 의존성이 발생하여 결합도가 높아지기 때문이며, 자유로운 내부 구현이 어려워지기 때문이다.

SUT의 동작을 인터페이스 기반으로 검증하면 내부 구현을 변경할 수 있는 자유도가 더 높아진다. 내부 구현은 구현에 대한 직접 검증이 아닌 공개된 인터페이스를 검증하는 것으로 충분하다.

## 완벽한 테스트를 지향하지 않기

테스트를 작성하다 보면 기대했던 것보다 더 많은 시간과 노력이 들어갈 수 있다. 따라서 테스트를 작성하는데 많은 비용이 들어가면 이를 인식하고 적정선에서 멈춰야 한다.

완벽한 테스트는 없다는 사실을 인정하고, 모든 경우의 수를 다루는 테스트를 작성하는 것이 아니라 치명적인 버그를 예방하고 이를 위해 경우의 수를 줄이는 데 집중해야 한다.

또한 테스트 코드 또한 하나의 코드로 바라봐야 하며, 테스트 코드 또한 장황하지 않고 비교적 변화에 잘 대응할 수 있도록 작성해야 한다.
